## 🐞 白屏事故：dev server 缓存了 DataTable.tsx 的「中间态」模块（第二次踩）

### 现象
用户在 5173 上刷新历史数据页 → **整页白屏**，控制台：
```
DataTable.tsx:67 Uncaught ReferenceError: wrapClassName is not defined
    at DataTable (DataTable.tsx:67:18)
  ... at AlarmTable ... at HistoryMode1 ... at AppHistory
```

### 结论：**不是代码问题，是 Vite dev server 的内存 transform 缓存**
- 磁盘上的 `DataTable.tsx` 是对的：`wrapClassName` 在 props 类型、解构、className 三处都在；
  `tsc -b` + `vite build` 都过；生产构建实机跑也正常（`is-fixed` 生效）。
- **确诊手法（可复用）**：直接 curl dev server 实际吐出的模块，跟磁盘比：
  ```bash
  curl -s http://localhost:5173/alert-screen/src/history/components/DataTable.tsx \
    | grep -n "wrapClassName\|wrapStyleOf"
  ```
  当时返回里 `wrapClassName` 只出现 1 次（只用在 `className:` 上），
  解构参数里**没有** —— 是一份「改了 className 但没加解构」的中间态。
  顺手确认 `AlarmTable.tsx` / `NestedGroups.tsx` / `table.css` 都是最新（只有这一个文件坏）。
- **修复**：对 `DataTable.tsx` 做一次**真实改动**（补了一段高度变体的文档注释）
  → 触发 Vite 重新 transform → 再 curl 确认解构里有 `wrapClassName` → 页面恢复。
  （注：纯改注释不影响产物，重建后 hash 不变 `index-CU9-MQ5k.js`。）

### 教训（**第二次**，见 2026-10-09 那条同类记录）
- 同一文件被**连续多次 Edit** 时（尤其中间还夹着一次 `EBUSY: resource busy or locked` 失败重试），
  Vite 的 watcher / transform 缓存可能停在某个中间版本，HMR 之后也不会自己纠正，
  **刷新页面没用**（缓存是 server 端的）。
- 所以：**能一次成型就一次成型**；改完多个文件后，如果页面报「某个明明已经定义了的变量未定义」，
  先 `curl` dev server 的模块内容确认，别去翻源码找 bug。
- 顺带记一下 `EBUSY: resource busy or locked` 也出现过一次（Edit 写文件被占用），
  重试即成功；但它会让「一次成型」的前提不成立，要留意。
